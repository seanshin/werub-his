# 환자여정 관제 콘솔 — 레이아웃·기능 재설계

- 작성: 2026-08-10
- 대상: `/journey-console` (FE `apps/web/src/app/(main)/journey-console/page.tsx` · BE `modules/journey-console`)
- 권한: ADMIN · EXECUTIVE (EXECUTIVE 는 환자명 강마스킹)

---

## 1. 배경 — 관제 화면인데 관제가 되지 않는다

관제(command console)의 존재 이유는 하나다. **지금 개입해야 할 사람을 즉시 찾는 것.**
현재 화면은 그 반대로 동작한다. 라이브 실측(2026-08-10 오후) 결과:

- 화면 상단은 **"평균 대기 0m"**, 임계 알림은 **9건**이라고 말한다.
- 같은 화면 아래 카드에는 **449분·1418분** 체류가 찍혀 있고, 접수대기 칸에만 **196명**이 쌓여 있다.
- DB 실측: 접수대기(WAITING) 196명의 **실제 평균 대기 352분(5시간 52분)**.

즉 **여섯 시간을 기다리는 196명이 관제 어디에도 표시되지 않는다.** 화면은 "정상"이라고 말하고 있다.
이 프로젝트가 반복해서 배운 것과 같은 계열이다 — *조용한 부재가 잘못된 값보다 위험하다*.

## 2. 실측 (2026-08-10 · 라이브 화면 + 운영 DB + 코드)

### 2.1 운영 DB

| 항목 | 값 |
|---|---:|
| 접수대기(WAITING) | **196명** |
| 접수대기 평균 경과 | **352분** |
| 오늘 완료(COMPLETED) | 329건 |
| └ 그중 `started_at` 있는 건 | **1건** |
| 오늘 수납(PAID·`paid_at` 오늘) | **0건** |
| PAID 인데 `paid_at` NULL | 17건 (전체 PAID 26건 중) |

### 2.2 화면이 표시한 값

| KPI | 표시 | 실제 |
|---|---|---|
| 평균 대기/재원 | **0m** | 접수대기 196명 평균 352분 |
| 오늘 수납 | **₩0** | 오늘 확정 수납 자체가 0건(데이터 결손) |
| 임계 알림 | 9건 | 접수 지연 **0건으로 집계**(감지 로직 없음) |

> 두 KPI 모두 **"표본이 없음"을 "0"으로 표시**하고 있다. 관제자는 이것을 "대기 없음 · 수납 없음"으로 읽는다.

## 3. 진단

### 3.1 레이아웃 (L)

| # | 문제 | 근거 |
|---|---|---|
| **L1** | **완료가 화면을 지배한다** — '수납 완료' 329장이 보드의 한 컬럼을 무한히 채운다. 이미 끝난 환자는 관제 대상이 아니다 | 라이브 스크린샷 |
| **L2** | **칸반이 세로 무한 스크롤** — 외래 530장이 전부 DOM 에 렌더된다. 스크롤 없이 보이는 건 컬럼당 6장 | 코드: `col.map(...)` 상한 없음 |
| **L3** | **정렬 기준이 없다** — 카드가 쿼리 순서대로 쌓인다. **가장 오래 기다린 환자가 맨 위로 오지 않는다** | 코드: `cards.filter(...)` 만 |
| **L4** | 빈 컬럼('진료중 0')도 동일 폭을 고정 점유 | `repeat(N, minmax(0,1fr))` |
| **L5** | '통합' 탭에서 외래·입원이 **세로로 적층** — 입원 보드는 530장을 지나야 나온다 | 라이브 확인(첫 화면에 입원 미노출) |
| **L6** | 드릴다운이 우측 360px 고정 — 선택 전엔 빈 박스, 선택 후에도 대부분 여백 | 라이브 확인 |
| **L7** | 체류가 **원시 분 단위**(`449분`·`1418분`). 수치 정본(`<Num>`) 미경유·시간 환산 없음 | 코드: `` `${card.stayMin}분` `` |

| # | 문제 | 근거 |
|---|---|---|
| **F1** 🔴 | **접수대기 지연을 감지하지 않는다** — flag 는 CALLED·CASHIER_WAITING·IN_CONSULT 에만 있고 **RECEPTION 은 없다**. 196명이 6시간을 기다려도 flag 0 | `journey-console.service.ts` flags 분기 |

| **F3** 🔴 | **오늘 수납 ₩0** — 표본 부재를 0 으로 표시. `paid_at` 결손 17건이 근인 | 코드 + DB 실측 |
| **F4** | **관제와 분석이 갈라져 있고 서로 링크가 없다** — `GET /analytics`(병목 top5·단계별 p50/p90·SLA 위반율·과별 top12·KTAS·병동 LOS)는 **별도 화면 `/flow-analytics`(176줄·nav 등재)로 이미 완성**돼 있다. 다만 관제에서 접수대기 196명을 보고도 *이게 상시 병목인지*를 같은 화면에서 판단할 수 없고, 양쪽 어디에도 상대 화면 링크가 없다 | 두 페이지 대조 |
| **F5** | **서버 필터 5종 미사용** — `dept·ward·insuranceType·minStayMin·minUnpaid` 를 컨트롤러가 받는데 FE 는 `track` 만 보낸다 | controller vs FE |
| **F6** | **임계 소스가 두 벌** — 보드는 하드코딩 `TH`(호출 10분·수납 30분·진료 40분·고액미수 50만·ALOS 7), 분석은 config `qi.targets.*`. **같은 화면인데 기준이 다르다** | 두 서비스 대조 |
| **F7** | **응급(ER) 트랙 부재** — 분석 서비스는 ER 을 집계하는데 보드는 OPD·IPD 뿐 | analytics `er()` vs board |
| **F8** | 드릴다운 액션이 '수납 상세' 링크 하나 — 관제에서 할 수 있는 개입이 없다 | FE |
| **F9** | 헤더 문구 `자동갱신 15s` 가 하드코딩. 실제는 보드 `pollMs('fast')`·KPI **20초 고정**(config 미경유) | FE |

## 4. 설계 원칙

1. **관제는 "조치 대상"만 보여준다.** 완료는 숫자로 충분하다. 카드는 개입이 필요한 사람에게만 준다.
2. **가장 위험한 사람이 맨 위에 온다.** 정렬은 임계 초과 → 체류 내림차순.
3. **모르면 모른다고 말한다.** 표본이 없으면 `0` 이 아니라 `산출 불가(n=0)`.
4. **임계는 한 곳에서 온다.** 보드·분석·알림이 같은 `qi.targets.*` 를 본다.
5. **표현은 정본을 경유한다.** 체류·금액·환자명·빈상태는 `<Num>`·`Money`·`PatientName`·`EmptyState`.

### 5.3 핵심 변경

| 변경 | 이유 |
|---|---|
| **완료 컬럼 → 카운트 타일** (카드 미렌더) | 329장이 관제 시야와 DOM 을 잡아먹는다. 필요하면 클릭으로 펼친다 |
| **컬럼당 상위 12장 + `[+N명 더보기]`** | 530장 렌더 제거. 관제는 상위 몇 명이면 충분하다 |
| **정렬 = 임계 초과 → 체류 내림차순** | 가장 오래 기다린 사람이 위로. 현재는 쿼리 순서 |
| **빈 컬럼 접기**(폭 축소·라벨만) | '진료중 0' 이 폭을 점유할 이유가 없다 |
| **트랙 탭에 '응급' 추가**, '전체'는 상단 요약 + 트랙별 전환 | 세로 적층으로 입원이 묻히는 문제 해소 |
| **드릴다운 = 선택 시 슬라이드-인 오버레이** | 빈 박스가 상시 360px 를 점유하지 않는다 |
| **체류 표기 `5시간 52분`**(`<Num>` 경유) | `352분` 은 읽어서 환산해야 한다 |
| **상황 스트립 sticky** | 스크롤해도 임계가 시야에서 사라지지 않는다 |

> 접근성: 임계는 색만으로 표시하지 않는다(⚠ 아이콘 + 텍스트 동반). 카드는 버튼이므로 키보드 포커스 순서를 정렬 순서와 일치시킨다.

## 6. 기능 보완 명세

### 6.1 P0 — 관제가 거짓말하지 않게 (BE 중심)

**F1 접수대기 지연 감지 신설**
```
RECEPTION 단계 stayMin > qi.targets.opdWaitMinutes  → flag 'WAIT_DELAY'
```
- KPI `alerts.WAIT_DELAY` 추가 · 임계 스트립·필터에 편입.
- 🔴 이것 하나로 현재 **감지 0 → 196건**이 된다. 배포 즉시 알림이 폭증하므로 **임계값 확인 후 반영**(§8 리스크).

**F2·F3 표본 부재를 0으로 쓰지 않기**
- `avgWaitMin`·`revenueToday` 를 `{ value, n }` 로 반환. `n === 0` 이면 FE 는 **`산출 불가(n=0)`** 로 표시(회색), 0 을 쓰지 않는다.
- `avgWaitMin` 의 `m < 600` 상한 제거 — **상한이 이상치를 지우는 게 아니라 실제 지연을 지운다**. 이상치는 p50/p90 로 다룬다(분석 서비스가 이미 그렇게 한다).
- 대기 평균의 **정의를 바꾼다**: 완료분 회고(`startedAt` 필요·표본 1건)가 아니라 **현재 대기 중인 환자의 경과**(표본 196건). 관제는 회고가 아니라 현재를 본다. 회고 통계는 `/flow-analytics` 소관(중복 구축 금지).

**F6 임계 정본 일원화**
- 보드 하드코딩 `TH` → `qi.targets.*` (`opdWaitMinutes`·`cashierWaitMinutes` 는 이미 존재). 신규 키는 `callDelayMinutes`·`consultDelayMinutes`·`highUnpaidAmount`·`longStayMultiplier`.
- 🔴 **ConfigRuntime DEFAULTS 등재 필수** — 등재하지 않으면 관리 화면에 뜨지 않고 가드 테스트가 실패한다(기존 교훈).

**F9 갱신 주기 표기 정합**
- KPI 폴링 `20_000` 하드코딩 → `pollMs()` 경유. 헤더 문구는 실제 주기를 렌더.

### 6.2 P1 — 레이아웃 재설계 (FE 중심)

§5 전량. 서버 변경 없음(정렬·상한·접기·오버레이는 FE). 단 **정렬 키는 서버가 이미 주는 `stayMin`/`flags`** 로 충분하다.

### 6.3 P2 — 관제 ↔ 분석 접합 (**중복 구축 금지**)

🔴 **분석 화면을 새로 만들지 않는다.** `/flow-analytics` 가 이미 병목 top5·단계별 p50/p90·위반율·과별 top12·KTAS·병동 LOS 를 전부 렌더한다. 문제는 *부재*가 아니라 *단절*이다.

| 조치 | 내용 |
|---|---|
| **병목 요약 스트립** | 관제 하단에 `/analytics` 의 **병목 top3만** 한 줄로(단계·위반율). 상세는 만들지 않는다 |
| **양방향 딥링크** | 관제 → `/flow-analytics`(현재 트랙·과 필터 전달) · 분석 → 관제(해당 단계로 필터된 보드) |
| **지연 호출** | 요약 스트립은 **접힘 기본**. 펼칠 때만 `/analytics` 호출(접힌 패널이 API 를 호출해 낭비·집계 왜곡을 낳던 기존 함정) |
| **기간 일치** | 관제 요약은 분석 기본값과 같은 7일. 서로 다른 기간을 보여주면 두 화면이 어긋난다 |

> 이 접합이 P0(임계 일원화)와 짝을 이룬다 — **같은 임계·같은 기간·같은 정의**를 두 화면이 공유해야 "관제에서 본 지연"과 "분석에서 본 위반율"이 같은 현실을 가리킨다.

### 6.4 P3 — 필터·응급 트랙·개입 액션

- **F5 필터 바**: 과·병동·보험·체류≥·미수납≥ (**서버가 이미 지원 — FE 배선만**) + '조치 필요만' 토글(flags 보유 카드만).
- **F7 응급 트랙**: 보드에 ER 레인 추가(도착→트리아지→처치→disposition). ER 베드 보드와는 **역할 분리** — 관제는 흐름·지연, 베드 보드는 병상 배정.
- **F8 개입 액션**: 드릴다운에 재호출·메모·담당자 통보. 🔴 **전부 기존 정본 EP 경유**(대기열 호출·알림). 관제 전용 쓰기 경로를 새로 만들지 않는다.
  - 🔴 알림 발송 시 `refId` 는 **uuid** 여야 한다(코드·일련번호 금지 — 넘기면 알림이 통째로 유실된다).

|---|---|---|---|
| **P0** | 접수지연 flag · 표본 부재 표기 · 임계 config 일원화 · 폴링 정합 | 관제가 실제 지연을 표시 | BE 소 · FE 소 |
| **P1** | 레이아웃 3존 재설계(완료 축약·상한·정렬·빈컬럼 접기·오버레이·체류 표기) | 한 화면에서 조치 대상 파악 | FE 중 |
| **P2** | 관제↔분석 접합(병목 top3 요약·양방향 딥링크·지연 호출) | 지연을 보고 원인까지 한 흐름에 | FE 소 |
| **P3** | 필터 바 · 응급 트랙 · 개입 액션 | 관제에서 조치까지 | FE 중 · BE 소 |

P0 는 단독 배포 가능하며 **가장 값이 크다**(현재 감지 0건인 지연을 드러낸다).

## 8. 리스크 · 주의

- 🔴 **P0 배포 즉시 임계 알림이 0 → 196 으로 뛴다.** 이는 결함 발견이지 회귀가 아니다. 다만 운영 혼란을 막기 위해 ①임계값을 `qi.targets.opdWaitMinutes` 로 먼저 확인하고 ②최초 배포는 **보드 flag 만** 켜고 알림 발송은 분리한다.
- 🔴 **현재 데이터가 데모 롤포워드 영향권**(`dev.demoDateRoll=true`)이라 체류 시각이 실제보다 부풀 수 있다. **임계값 튜닝은 실 서비스 데이터로 해야 한다** — 지금 값으로 임계를 정하면 실운영에서 어긋난다.
- `paid_at` 결손 17건은 **이 화면의 문제가 아니라 청구 데이터 문제**다. 관제는 "산출 불가"로 정직하게 표시하고, 결손 자체는 데이터 정합성 트랙으로 넘긴다.
- 완료 카드 미렌더는 **정보 삭제가 아니라 기본 접힘**이다. 카운트 클릭으로 항상 펼칠 수 있어야 한다.
- 정렬 변경은 관제자의 근육 기억을 바꾼다. 정렬 기준을 **화면에 명시**한다(“체류 긴 순”).
- EXECUTIVE 강마스킹은 재설계 후에도 유지 — 카드·드릴다운·분석 어디에도 실명이 새지 않아야 한다(계약 테스트).

### 11.2 ⏳ 미착수 — 관제 메모 · 담당자 통보

의도적으로 남긴다. 둘 다 **새 쓰기 경로를 요구**해 §6.4 원칙("관제 전용 쓰기 경로를 새로 만들지 않는다")과 충돌한다.

- **관제 메모**: 저장할 정본 모델이 없다. 관제 전용 메모 테이블 신설은 기록의 이중화를 낳는다(임상 기록은 차트, 운영 기록은 어디?). **어디에 남길지가 먼저 결정돼야 한다.**
- **담당자 통보**: 알림 발송 자체는 가능하나 ①누구에게(주치의? 원무? 병동?) ②중복 억제 정책 ③`refId` 결속 대상을 정해야 한다. 🔴 `refId` 는 uuid 여야 하며 코드·일련번호를 넘기면 **알림이 통째로 유실**된다.

### 11.3 남은 관찰

- **임계값은 실 서비스 데이터로 튜닝해야 한다.** 현재 값(대기 30분)에서 접수지연이 194건인데, 이는 `dev.demoDateRoll` 영향권 데이터다. 실운영 개통 후 재조정 대상.
- 접수지연 194건은 **알림으로 발송하지 않는다**(보드 flag·임계 스트립까지만). 알림 편입은 임계 튜닝 후 운영 판단.
