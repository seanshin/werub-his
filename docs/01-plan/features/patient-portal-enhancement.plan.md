## 2. 목표

1. **알림 센터(웹)**: 기존 알림 API를 웹 포털에 배선 — 헤더 벨+미읽음 배지, 알림 목록, 알림 설정("준비 중" 해소). 웹·모바일 동일 데이터.
2. **입원 생활 카드**: 입원 중(journey ⑤) 환자에게 오늘 식사(식이 정보)·입원비 중간정산·면회/생활 안내를 포털 홈 입원 카드군에 추가(회진·투약 카드는 기구현 — v1.3).
3. **복약 리마인더**: 복약 일정 기반 시간대별 알림(모바일 푸시 + 웹 인앱) → 복약 체크로 연결. 설정에서 on/off.
4. **보험 청구 서류 패키지**: "실손보험 청구" 원클릭 — 필요 서류 세트를 묶음 신청·묶음 다운로드.
5. **처방·투약 AI 쉬운 설명**: 처방약마다 "이 약은 무엇인지·어떻게 먹는지·주의할 점"을 e약은요(공공 DB) 근거 + LLM 쉬운 말 재구성으로 제공 — 약 단위 + 처방전 단위("이번 처방 한눈에").
6. **비파괴·무중단**: BE 신설 기능은 config 게이트로 점진 활성화(F-1은 FE 배선뿐이라 게이트 없음), 기존 화면·EP 변경 없음(추가만).

**비목표**: 보험사 전자전송(실손24 등 외부 연계 — P2 이후 별도), 의사 답변형 메시지(별도 기획), 처방전 리필의 법적 예외 처리(현행법상 재진 필요 — 비대면진료 기존 흐름 유지), 알림 인프라 신설(기존 Notification 재사용), **복약지도 대체(약사 소관 — AI 설명은 공공 정보의 쉬운 말 재구성에 한정, 진단·용법 변경 권고 금지)**.

## 3. 설계

### 3.1 F-1 웹 알림 센터 (P0)

- **FE만**: `portal/page.tsx` 헤더의 **기존 벨 버튼(onClick 없는 껍데기 — v1.4 발견)에 배선** + `unread-count` 배지(60초 폴링 — SSE 미사용 확정) → 알림 패널(목록·읽음·전체읽음) → MoreTab '알림 설정' → 설정 화면(`GET/PUT notifications/settings`).
- 알림 클릭 → 딥링크: `linkTo` 필드(기존 알림 payload) 기준 탭/세그먼트 이동 (예: 문진표 미완료 → 진료>문진표).
- 인증 주의: 알림 API는 `PatientAccountAuthGuard`(환자계정 JWT) — **레거시 포털 토큰(MRN+생년월일)으로 로그인한 세션은 미노출**(계정 가입 유도 배너). 열린 결정 §7-1.

### 3.2 F-2 복약 리마인더 (P1)

- **발송 파이프라인(신설·소형)**: cron 매 30분(선례: `chronic-recall-cron`) → `Prescription.status='ACTIVE'` 기반 복약 일정(기존 `getMedicationSchedule` 로직 재사용 — frequency 문자열 → `parseFrequencySlots` 슬롯) 중 리마인더 켠(opt-in) 환자의 도래 슬롯 추출 → **이벤트 발행 → notification 리스너 핸들러가** `PatientNotification` 생성+FCM 푸시(v1.6 — 기존 환자 알림 발송 관례가 이벤트 리스너 방식임을 확인, 설계서 §3.2). **대상 = 활성 admission이 없는 환자**(입원 중 원내 투약은 간호 MAR 소관 — 이중 알림 방지, §7-11 종결)·계정당 일일 상한.
- **슬롯→발송 시각 매핑**: 일정은 "아침 식후" 등 슬롯 단위(시각 아님) — 슬롯별 기본 시각을 config로(`{아침:08:00, 점심:12:30, 저녁:18:30, 취침전:21:30}`). 환자별 시각 커스텀은 후속(P1은 고정 시각).
- 알림 탭 → 복약 체크(`medication-check` 기존 POST) — "복용 완료" 원탭.
- **복약 체크 저장소(신설 1)**: 현재 `checkMedication`은 **포털 감사 로그에만 기록**(조회 가능한 테이블 없음) → `MedicationCheckLog(patientId, prescriptionId, slotDate, slot, taken)` 신설(manual SQL). 용도 3가지: ① 리마인더 **멱등 키**(동일 슬롯 재발송 방지 — 발송 기록 겸용) ② 복약 화면 "오늘 체크 여부" 표시 ③ 순응도 추이(후속). 기존 감사 로그 기록은 유지(회귀 0).
- 설정: `NotificationSetting`에 `type='MEDICATION_REMINDER'` 행 — **스키마 변경 없음**(행 단위 모델이라 값 추가로 흡수).
- 발송 전 재검증: 처방 ACTIVE 여부·퇴원/취소 확인 후 발송(§5).
- config: `portal.medicationReminder=false` 기본 OFF.

### 3.3 F-3 입원 생활 탭 (P0~P1)

포털 홈(HomeTab)의 기존 입원 카드군(히어로·투약·회진 기구현)에 카드 추가. 포털 EP 신설 **2개**(모두 읽기 전용·본인 admission 스코프):

| 섹션 | 신설 EP | 소스 | 비고 |
|------|---------|------|------|
| 오늘/내일 식사 | `GET /portal/inpatient/meals` | `MealOrder`(끼니·식이종류·배송상태)+`DietOrder`(제한·칼로리) | **v1.4 교정: 메뉴 텍스트(음식명) 데이터 부재** — "식이 정보 카드"(식이 종류·끼니 상태·제한)로 범위 확정, 메뉴 표 연동은 영양팀 데이터 확충 후 |
| ~~회진~~ | ~~신설 EP~~ → **v1.3 제외**: 포털 홈 lifecycle이 최근 회진(경과기록)을 이미 노출 — 신설 불필요 | 기존 journey/status | 회진 **예정** 시간은 §7-3 유지(정적 안내 vs 모델 신설) |
| 입원비 중간정산 | `GET /portal/inpatient/interim-bill` | 기존 `getErpInvoice({ chartNo, interim:true })` 재사용 | ERP=진료비 SoT(D-6) — HIS는 표시만. "확정액 아님" 고지 필수. **chartNo는 세션 환자에서 서버가 주입**(쿼리 파라미터 노출 금지 — IDOR). ERP 미구성/`available:false` 시 섹션 비노출(에러 아님) |
| 면회·생활 안내 | 정적/CMS | 기존 병원안내(custom page) 재사용 | 신설 없음 |

- 노출 조건: 활성 admission 보유 시에만 섹션 렌더(기존 journey 판정 재사용). 보호자 위임 시 민감정보 필터 통과분만.
- config: `portal.inpatientLife=false` 기본 OFF → 병동별 시범 후 전체.

### 3.4 F-4 실손보험 청구 서류 패키지 (P1)

- **묶음 신청**: 서비스탭 서류발급에 "실손보험 청구 세트" 카드 → 대상 기간/진료 선택 → 구성 서류 자동 제안:
  - 외래: 진료비 세부산정내역서 + 진료비 영수증 + 통원확인서 (+처방전 사본 선택)
  - 입원: 세부산정내역서 + 영수증 + 입퇴원확인서 (+진단서는 유료·의사 작성이므로 별도 신청 유도)
- **구현**: `POST /portal/documents/request-bundle` — 내부적으로 기존 요청을 **N건 생성 + bundleId 묶기**(`DocumentRequest`에 `bundleId` 컬럼 1개 추가 — manual SQL, deploy 규칙 준수). 발급 파이프라인·수수료 엔진·진위QR 전부 기존 재사용.
- **서류 type 보강 필요**: 현행 `DocumentRequest.type`은 `MEDICAL_RECORD·DIAGNOSIS_CERT·OPINION·RECEIPT·TAX_INVOICE·ADMISSION_CERT` — 실손 세트의 **진료비 세부산정내역서(`DETAILED_BILL`)·통원확인서(`ATTENDANCE_CERT`)가 없음**. VarChar라 값 추가는 무스키마이나, **발급 파이프라인에 두 문서의 생성 핸들러(헤드리스PDF 템플릿) 추가**가 실제 작업량 — 세부산정내역서는 기존 영수증 fullCopay 5열 데이터 재사용 가능.
- **묶음 다운로드**: 전 구성원 READY 시 "전체 다운로드"(zip 또는 병합 PDF — 열린 결정 §7-4) + 알림(F-1 연계: "보험 청구 서류가 준비되었습니다").
- 세부내역서·통원확인서는 **즉시 READY** — 단 v1.6 검증: 현행 파이프라인에 자동발급은 없음(전량 직원 처리)이므로, 발급 파이프라인(스냅샷→IssuedDocument→진위QR)을 서버가 직원 개입 없이 즉시 수행하는 **자동발급 분기를 신설**(설계서 §4.2). 직원 작성 필요 문서만 대기 — 부분 다운로드 허용.

### 3.5 F-7 처방·투약 AI 쉬운 설명 (P1)

투약관리 탭·처방 이력·퇴원약(dischargeMedications)에 **"쉽게 보기"** 를 붙인다. 원칙: **AI는 공공 데이터를 쉬운 말로 재구성만** — 사실은 e약은요에서, 문장은 LLM이.

**T-0 ~~선행 과제~~ → ✅ 해결 (v1.5 — 2026-07-07 운영 테스트, 설계서 §5.6)**
e약은요 조회 키(품목기준코드)가 HIS 마스터에 없었으나, **운영 실측으로 기존 EP 2-hop 체인 확정 — WeRU.B 협의·스키마 변경·공공 매핑 임포트 전부 불필요**: `insuranceCode`(선행 0 제거) → `drug-master`가 `item_code`(품목기준코드) 반환 → `e-drug-info/{item_code}` 정확 조회(개정일 `update_de`·disclaimer 정본 동봉). 해석 실패 품목은 아래 4의 폴백으로 안전(명칭 검색은 오매칭 위험으로 자동 사용 금지).

**약 단위 설명** — `GET /portal/medications/:id/explain`
1. 처방 항목 → T-0 경로로 **itemSeq 확보**
2. e약은요 조회(기존 `eDrugInfo()` 서비스 재사용 — 포털용 EP 신설, 직원 롤 EP 직접 개방 금지)
3. LLM(WeRU.B Ollama)이 e약은요 원문 + 처방 용법을 입력으로 **환자 눈높이 4단 구성** 생성: ① 무슨 약(효능) ② 어떻게 먹나(이번 처방 용법 기준) ③ 주의할 점 ④ 이런 증상이면 연락
4. **환각 방지**: e약은요 원문이 프롬프트에 grounding으로 반드시 포함, **원문 미존재 시(itemSeq 매핑 실패 등) AI 생성 금지** — "정보 준비 중, 약사와 상담하세요" 폴백. 출처("식약처 e약은요") 표기.

**처방전 단위 "이번 처방 한눈에"** — `POST /portal/prescriptions/:encounterId/explain` (처방전 단위 = encounter 1건의 처방 묶음. 비동기 잡·폴링 — 포뮬러리 AI 패턴 재사용)
- 처방전의 전 약품에 대해: 각 약의 역할 한 줄 + **DUR 점검 결과(기존 `dur/check`)를 쉬운 말로**(예: "임신 중이면 의사에게 알리세요") + 전체 복용 스케줄 표.
- 다건 LLM 호출이므로 nginx 60s 함정 대상 — jobId 발급→폴링(§0 포뮬러리 패턴). AI 프록시 NDJSON 스트리밍 라인 병합 함정 동일 적용.

**캐시·비용**: 약 단위 설명의 ①③④는 환자 무관 → **약품 코드 단위 캐시**(DB 테이블 1개 `DrugExplainCache(codeId, content, sourceVersion, createdAt)` 또는 Redis) — 동일 약 재생성 없음. ②(용법)만 처방별 실시간 조립(LLM 불필요·템플릿).

**규제 경계(checkup-explainer 프레임 차용)**:
- 「웰니스(정보 제공)」 한정 — 진단·효과 판정·용법 변경 권고 문장 금지(프롬프트 가드 + 금칙어 후처리).
- 하단 고정 고지: "이 설명은 식약처 공개 정보를 알기 쉽게 정리한 것으로, 복약지도를 대체하지 않습니다. 정확한 복약 상담은 약사에게."
- 소비자 노출 전 **약제부 샘플 검수**(상위 처방 빈도 N개 약품의 생성 결과 검토) — 열린 결정 §7-7.

**연계**: F-2 복약 리마인더 알림에서 약명 탭 → 해당 약 쉬운 설명으로 딥링크. 기존 `ai/ask` 챗봇에는 "내 약 설명" 진입 버튼만 추가(중복 구현 금지).

config: `portal.aiDrugExplain=false` 기본 OFF.

### 3.6 F-5 만성 재진 원스톱 (P2·스케치)

- 만성탭(당뇨 등)에서 "재진 예약" → 예약 + 사전 문진 + **지난 처방 요약 첨부**(의사 참고용 메모, 처방 자동복사 아님 — 처방권 침해 금지) 원플로우.
- 법적 경계: 처방전 리필 불가(재진 필수) — 본 기능은 **예약·정보 전달 단축**에 한정.

### 3.7 F-6 내 건강기록 내보내기 (P2·스케치)

- `GET /portal/my-records/export` — 본인 기록 FHIR R4 번들(진단·투약·검사·알레르기·예방접종) 생성 → 암호화 다운로드(PACS export의 토큰·만료 패턴 차용).
- 마이헬스웨이 연계는 국가 게이트웨이 스펙 확정 후 별도 기획. 개인정보 반출이므로 **본인 재인증(step-up) + 감사 로그** 필수.

## 6. 검증

- F-1: 미읽음 배지 수 = API unread-count 일치, 읽음 처리 반영, 설정 저장·재조회, 레거시 세션 배너 노출.
- F-2: 슬롯 도래 시 알림 1회만(MedicationCheckLog 멱등), 퇴원/중단 처방 미발송, 체크 시 로그 테이블 기록 + 기존 감사 로그 유지, 복약 화면에 오늘 체크 상태 표시.
- F-3: 타 환자 admission 접근 차단(세션 주입 확인), 식이 정보·중간정산 실데이터 대조(운영 응답 대조 — 위젯 규약 준수), 비입원 환자 카드 미노출.
- F-4: 묶음 신청→구성 요청 N건 생성·bundleId 일치, 전체 READY 시 묶음 다운로드, 부분 READY 시 부분 다운로드, 진위QR 검증 통과.

## 7. 열린 결정

1. **알림 API 가드**: 레거시 포털 토큰에도 알림 열람 허용(PortalOrPatientGuard로 확장) vs 환자계정 전용 유지(가입 유도) — 보안·계정 전환 전략과 연동.
2. ~~리마인더 멱등 저장소~~ → **v1.2 결정: `MedicationCheckLog` 테이블 신설**. 보존 기간은 설계 기본안 **1년**(월 1회 삭제 배치, 설계서 §3.1) — 이견 시만 재론.
3. **회진 예정 시간**: 병동별 정적 안내(즉시 가능) vs 회진 예정 모델 신설(의사 일정 연동 — 별도 기획 규모).
4. ~~묶음 다운로드 형식~~ → **설계 확정(zip)**: 병합 PDF는 진위QR 개별 검증 불가(설계서 §4.3).
5. ~~모바일 반영 시점~~ → **v1.6 종결: 웹 검증 후 별도 설계로 이연**(F-2 푸시·딥링크는 기존 앱 코드로 자동 동작 — 설계서 §7.2).
6. F-6 반출 범위: 전체 기록 vs 기간/카테고리 선택 — 개인정보 최소화 원칙과 사용성.
7. **F-7 검수·법무 게이트**: 약제부 샘플 검수 범위(상위 20종 vs 전 캐시 생성분 승인제) + 「웰니스(정보 제공)」 법무 확인을 checkup-explainer 건과 묶어서 진행할지 — 묶으면 게이트 1회로 두 기능 해소.
8. ~~F-7 캐시 저장소~~ → **설계 확정(DB 테이블)**: DDL까지 확정(설계서 §5.2 — 감사·`update_de` 버전 관리).
9. **🔴 F-7 노출 시점 (구현 전 결정 필수)**: 처방(원외처방전 발행) 즉시 vs 수납 완료 후 — 설계서 §5.5는 투약 화면 전 카드 노출(사실상 즉시)로 그려져 있어 **결정이 나면 조건 렌더만 추가**하면 되지만, 미결 상태로 구현 착수 금지.

11. ~~F-2 리마인더 대상 처방 범위~~ → **v1.6 종결**: 판별 필드 부재 확인 — 규칙 대체("활성 admission 없는 환자의 ACTIVE 처방" + 중립 문구, 설계서 §3.2).
