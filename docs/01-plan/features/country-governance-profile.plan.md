# 국가 거버넌스 프로파일 — 레이아웃은 언어가 아니라 거버넌스에서 갈린다

작성 2026-09-07 · 상위 `ui-locale-i18n.plan.md`(언어 축) · 형제 `arabic-rtl-track.plan.md`(AE 에디션)
· 선례 `hospital-opening-*`(개원 축 국가 분기)

---

## §0 문제 — AE 를 특수 사례로 만들면 세 번째 나라에서 또 복제한다

아랍어 트랙(`arabic-rtl-track.plan.md`)은 "AE 는 업무가 다르니 별도 화면"이라고 정리했다.
맞지만 **일반화가 빠졌다.** 그 문서대로 `app/(ae)/**` 만 만들면:

- 사우디·카타르가 오면 `app/(sa)/**` 를 또 만든다 — 화면이 국가 수만큼 복제된다
- **KR 은 이름 없는 기본값으로 남는다** — 가장 위험한 상태다(§1)

🔴 **레이아웃이 국가별로 갈리는 이유는 언어(RTL)가 아니라 거버넌스다.**
RTL 은 레이아웃 4층위 중 **한 층**일 뿐이고(§2), 진짜 큰 차이는 지불자 구조·관할 수·코드 체계가
**화면에 어떤 블록이 있어야 하는가**를 바꾸는 데서 온다.

## §1 실측 (2026-09-07) — KR 이 기본값으로 박혀 있다

| 관측 | 실측 | 읽는 법 |
|------|-----:|---------|
| 국가로 갈리는 코드(파일) | **5** | 전부 개원 모듈(`opening.*` 3 + `config-runtime` + `/admin/opening`) |
| 청구 모듈 국가 분기 | **0** | |
| 보험·자격 모듈 국가 분기 | **0** | |
| 결정 등록부 국가 분기 | **0** | |
| 개원 레지스트리 `countries` 항목 | 61 | 국가 축이 **이미 작동하는 유일한 선례** |
| 한국 전용 개념 | **4,974** | KR_ONLY 2,077(41.8%) · **KR_RULE 1,982**(39.9%) · UNKNOWN 915(18.4%) |
| 한국 전용 개념을 가진 화면 | **97면** | KR_ONLY 68 |
| Prisma `country` 필드 | **4** | 그중 하나는 `@default("KOR")` — **한국이 하드코딩 기본값** |
| 법정 인쇄 서식 | 6면 | 전부 한국 서식(불변 규약) |

### 🔴 이 표가 말하는 것

**개원 축만 국가를 안다. 진료·청구·자격은 "한국이 유일한 세계"라고 가정하고 있다.**

이건 결함이 아니다 — 한국 병원용으로 만들었으니 당연하다. 문제는 **그 가정이 코드에 표시돼 있지
않다**는 것이다. `본인부담` 246곳은 자기가 KR 전용이라는 사실을 모른다. 그래서:

- AE 화면을 만들 때 **무엇을 빼야 하는지 목록이 없다**(34면·566곳을 눈으로 골라야 한다)
- 새 나라가 올 때마다 **같은 발굴을 처음부터** 한다
- KR 규칙을 고칠 때 **다른 나라에 영향이 가는지 알 수 없다**

🔴 **이름 없는 기본값이 가장 위험하다** — 같은 사실에 정본이 둘인 것(P12)보다,
정본이 하나인데 **그게 특정 국가 전용이라는 사실이 안 적힌 것**이 더 오래 산다.

### 🔴 이 표의 수치는 `node scripts/country-concept-scan.mjs` 로 재현한다 (G1)

초판(2026-09-07 오전)은 손 grep 으로 "API 566 · FE 190 · 화면 34면"이라 적었는데
**재현되지 않았다.** KCD 86·요양기관 29·산정특례 18·주민등록 18·FE 다수는 정확히 맞았으나
**copay 246(재측 358)·HIRA 122(재측 206)** 은 어떤 조합으로도 안 맞고, **세는 규칙을 적어두지
않아 어느 쪽이 맞는지 판정할 근거가 없었다.** `system-scale.mjs` 가 만들어진 것과 같은 상황이다.
→ 규칙을 스크립트에 못박고 동결값을 뒀다(`--check`/`--freeze`).

🔴 **KR_ONLY 와 KR_RULE 을 반드시 갈라 읽는다.** `본인부담`·`copay` 1,202 은 **어느 나라에나
있는 개념**이고 갈라야 할 것은 **산정 규칙**이다. 섞으면 "AE 에서 본인부담 블록을 빼라"는
거짓 결론이 나온다. 실제로 본인부담 엔진은 **이미 국가 중립**이다(요율은 SystemConfig·정본은
`resolveCopayRate` 하나) — 바꿀 자리는 `CopayCategory` 어휘·`InsuranceType` DB enum·
`EligibilityProvider.source` **셋뿐**이다.

🔴 **용어 스캔이 구조적으로 못 잡는 부류가 따로 있다**(G1 이 별도 계측): `ko-KR` 하드코딩
**156파일**(개념 보유 화면보다 많다) · `+82` 26 · **KR 전화 정규식(AE 번호가 폼에서 막힌다)** ·
`VISA_TYPES` · 초성 인덱스 · 카드사 목록. 한국어 낱말이 **없어서** 안 걸린다.
**분모를 알 수 없는 탐지기라 위 집계에 더하지 않았다** — 별도 축으로 본다.

## §2 레이아웃 4층위 — 어느 층이 무엇 때문에 갈리는가

사람 지적("각 국가별 거버넌스에 따른 레이아웃")을 층으로 나눈다. **층마다 결정 근거가 다르다.**

| 층 | 무엇 | 갈리는 근거 | 현재 상태 |
|----|------|-------------|-----------|
| **L1 방향** | LTR / RTL | **언어** | ar 팩 보존·에디션 트랙 R-A0 |
| **L2 서식** | 숫자·날짜·이름·통화 표기 | **로케일** | `localeTagOf` + 표시 부품 100파일(정본 있음) |
| **L3 구조** | 화면에 **어떤 블록이 있는가** | 🔴 **거버넌스** | **없음 — 이 문서의 대상** |
| **L4 동선** | 화면 **순서·분기** | 🔴 **거버넌스** | **없음 — 이 문서의 대상** |

L1·L2 는 언어 축이 이미 다룬다. **L3·L4 가 비어 있다.**

### 거버넌스 → 레이아웃 사슬 (왜 블록이 달라지는가)

| 거버넌스 항목 | KR | AE(예) | 바뀌는 레이아웃 |
|---------------|-----|--------|-----------------|
| **지불자 구조** | 단일(건보공단) | 다수 민간 보험사 | 접수: 자격조회 1회 → **보험사·플랜 선택 + 사전승인 블록** |
| **본인부담 산정** | 고시 급여기준·산정특례 | 플랜별 코페이·연간 한도 | 수납: 산정특례 배지 → **플랜 한도 잔액** |
| **관할** | 1(복지부·심평원) | **3**(DHA·DoH·MOHAP) | 보고: 단일 제출 → **제출처 선택 필수** |
| **진단 코드** | KCD-8 | ICD-10-AM 계열 | 진단 입력 위젯·검색 정본 |
| **처치·수가** | 상대가치점수 | CPT 계열 | 오더·청구 라인 |
| **신원 체계** | 주민등록번호 | Emirates ID·여권 | 환자 등록 폼 필드 구성 |
| **법정 서식** | 시행규칙 별지 | 관할별 서식 | 인쇄 6면 |
| **역법·주말** | 양력·토일 | 🔴 **미조사**(아래 주 참조) | 일정·근무표 |

🔴 **이 표의 오른쪽 열이 "화면을 다시 그려야 하는 이유"다.** 좌우 반전이 아니다.

🔴 **정정(2026-09-07)**: 이 표의 AE 열에 **조사하지 않은 값**이 있었다 — 주말을 "금토"라고
적었는데 **UAE 는 2022년 토일로 바뀌었다**(G1 이 지적). 이 문서가 §3.1 에서 "조사한 것만
적는다"고 해놓고 스스로 어긴 자리다. AE 열은 **설계 방향을 보이기 위한 예시**이지 실측이
아니며, `AE_PROFILE` 선언(G3)은 **조사를 거친 값**만 담는다. 조사 없이 프로파일에 넣으면
지어낸 값이 시드를 타고 정책이 된다(개원 축에서 실제로 겪은 일이다).

## §3 설계 — 거버넌스 프로파일

### §3.1 정본

`packages/shared/src/governance/profile.ts` — **국가별 거버넌스를 데이터로 선언**한다.

```ts
export interface GovernanceProfile {
  country: CountryCode;              // 'KR' | 'AE' | …
  label: string;
  payer: {
    model: 'SINGLE' | 'MULTI';       // 단일 지불자 / 다보험사
    eligibilityCheck: 'NATIONAL' | 'PER_INSURER' | 'NONE';
    priorAuth: boolean;              // 사전승인 블록 필요 여부
  };
  jurisdictions: Jurisdiction[];     // KR 1 / AE 3 — 길이가 곧 "제출처 선택 필요"
  coding: { diagnosis: string; procedure: string };
  identity: IdentityField[];         // 등록 폼 필드 구성
  forms: { statutoryPrint: boolean };
  calendar: { weekend: number[]; secondaryEra?: string };
  // 🔴 조사한 것만 적는다 — 법령 조문·수수료·처리기한은 넣지 않는다(개원 축 선례).
}
```

🔴 **프로파일은 값을 선언할 뿐 판단하지 않는다.** "이 나라는 사전승인이 있다"까지가 프로파일이고,
"그래서 이 환자는 승인이 필요한가"는 기존 도메인 로직이 정한다(정본을 옮기지 않는다).

#### 🔴 필드의 뜻을 여기서 못박는다 (G0 실측에서 드러난 공백)

이 절이 없어서 G0 이 필드마다 **뜻을 스스로 정해야 했다.** 각 필드는 **레이아웃을 무엇으로 가르는가**로 정의한다 —
"세상에 몇 개가 있는가"가 아니다. 이 구분을 흐리면 프로파일이 거짓말을 한다.

| 필드 | 뜻 | 잘못 읽으면 |
|------|-----|-------------|
| `payer.model` | **접수 화면에 보험사·플랜 선택 UI 가 필요한가** | "지불자 수"로 읽으면 KR 도 4개다(건보·의료급여·산재·자보) → `MULTI` 가 되어 없는 UI 를 요구한다 |
| `jurisdictions` | **제출처를 사람이 골라야 하는 단위** | "규제 기관 수"로 읽으면 KR 도 2개다(복지부·심평원) → `length>1` 로 제출처 선택 화면이 생긴다. 실제로는 청구 EDI 가 심평원 하나다 |
| `identity` | **등록 폼에 그리는 필드** | 모델 필드로 읽으면 `Patient.ci`·`nationalIdType` 까지 들어와 화면과 어긋난다 |
| `coding.*` | **코드 검색·입력 위젯이 무엇을 부르는가** | — |

🔴 **`calendar.secondaryEra` 는 `string | null` 필수다**(optional 아님). optional 로 두면
**"없다"와 "아직 안 정했다"가 구분되지 않는다**(3상태 규칙). 조정치에서는 `undefined`=조정 없음 /
`null`=명시적으로 없음으로 갈린다. — G0 이 발견해 고친 자리.

### §3.2 🔴 프로파일은 **국가 템플릿 + 기관 조정** 두 층이다 (사람 결정 2026-09-07)

사람 결정: **"운영 초기에 결정되고, 각각의 의료기관 세팅 시에 조정되는 형태."**
→ 🧑G3 해소: **국가는 기관 속성이다**(환자 속성이 아니다). 행 단위 분기가 아니라 슬롯 설계가 맞다.

실측이 이 형태를 이미 지탱한다:

| 관측 | 실측 | 함의 |
|------|------|------|
| 멀티테넌트 | **아니다**(Hospital 모델 없음·`tenantId` 0) | **한 설치본 = 한 기관** |
| `hospital.country` | SystemConfig 키·기본값 `'KR'`·개원 모듈만 소비 | 기관 조정 경로가 **이미 있다** |
| 기관 조정 일반 패턴 | SystemConfig 소비처 184 | 프로파일도 같은 경로 |
| 출처 배지 선례 | 개원 축(`source` 를 항목마다 들고 다님) | **어디서 온 값인지** 말하는 방식이 있다 |

```
국가 템플릿(KR_PROFILE·AE_PROFILE …)   ← 코드에 선언·조사한 것만
        ↓ 세팅 시 국가 선택으로 깔린다
기관 조정치(SystemConfig `gov.*`)      ← 기관이 항목별로 덮는다
        ↓
유효 프로파일(effective)               ← 화면·슬롯이 보는 값
```

🔴 **기본값으로 떨어진 것을 조용히 하지 않는다.** 조정하지 않은 항목은 국가 기본값인데,
화면이 그 사실을 말해야 한다(개원 화면이 이미 그렇게 한다 — "기관 국가가 설정되지 않아
기본값으로 보고 있습니다"). 항목마다 **출처 배지**: `국가 기본` / `기관 조정`.
다만 **막지 않는다** — 미조정이 곧 결함은 아니다.

### §3.2-b 🔴 운영 중 변경은 과거를 다시 쓰지 않는다

세팅 시점 결정이라도 **나중에 바뀐다**(보험 계약 변경·관할 추가). 그때:

- **일어난 사실은 소급하지 않는다** — 이미 발생한 청구·기록은 그때의 규칙으로 남는다
- 프로파일 변경에는 **발효 시점**이 붙는다(결정 경로 엔진의 버전 스냅샷 선례)
- 🔴 과거 데이터를 새 프로파일로 읽어 통계를 내면 **없던 실적이 생기거나 사라진다** —
  기간이 프로파일 발효 전후에 걸치면 그 사실을 화면이 밝힌다(분모 병기와 같은 규약)

### §3.3 KR 도 프로파일이다 — 이름을 붙이는 것이 첫 작업

🔴 **KR 프로파일을 만드는 것만으로 동작이 바뀌면 안 된다.** G0 은 순수한 이름 붙이기다.
지금 화면이 하는 일을 그대로 선언하면 `KR_PROFILE` 이 나온다. 이 단계의 성공 기준은
**현행 화면·테스트가 하나도 안 바뀌는 것**이다.

### §3.4 L3 슬롯 — 구조를 프로파일이 정한다

화면을 국가별로 복제하지 않고, **블록 존재 여부**를 프로파일이 정한다.

```tsx
<GovernanceSlot when={(p) => p.payer.priorAuth}>
  <PriorAuthBlock />
</GovernanceSlot>
```

🔴 **숨기는 것과 없는 것은 다르다**(운영 모드 축의 교훈). 다만 이 축에서는 **★G1 이 해소됐다** —
기관마다 세팅한다는 것은 **한 설치본 = 한 기관**을 뜻하고(실측: 멀티테넌트 아님·`tenantId` 0),
그러면 배포는 이미 기관 단위로 갈려 있다. **런타임 설정으로 간다.**

🔴 그래도 운영 모드 축과 다른 점을 분명히 한다: 거기서 숨긴 것은 **민감 값**(리얼 전환 전 노출
금지)이라 번들에 남는 것 자체가 위험이었다. 여기서 숨기는 것은 **다른 나라의 화면 블록**이라
번들에 남아도 유출 위험이 아니다. 그래서 재배포 없이 설정으로 바꿀 수 있다 —
**이 판단이 뒤집히는 경우는 하나**: 프로파일이 원내 계약·수가 같은 비공개 값을 담게 될 때.

🔴 **예외 하나가 실측됐다**(G1): `InsuranceType` 은 **Prisma enum** 이라 값을 늘리려면
마이그레이션이 필요하다 — 런타임 설정으로 못 바꾼다. 프로파일이 이런 항목을 가리킬 때는
"설정으로 바뀐다"고 말하면 거짓이다. 해당 항목은 **마이그레이션 층**임을 세팅 화면이 밝힌다.
그때는 담지 말고 기존 도메인 설정에 둔다(§3.1 "프로파일은 값을 선언할 뿐 판단하지 않는다").

### §3.5 언제 슬롯이고 언제 에디션인가

| 차이 크기 | 방식 | 예 |
|-----------|------|-----|
| 블록 1~2개 유무 | **L3 슬롯** | 산정특례 배지·사전승인 블록 |
| 필드 구성이 다름 | **L3 슬롯**(필드 목록을 프로파일이 줌) | 환자 등록 신원 필드 |
| **동선 자체가 다름** | **에디션**(`app/(ae)/**`) | 접수→보험사→플랜→사전승인→진료 |

🔴 **에디션은 최후 수단이다.** 슬롯으로 되는 것을 에디션으로 만들면 화면이 국가 수만큼 늘어나고,
KR 화면의 개선이 다른 나라에 영원히 반영되지 않는다(아랍어 트랙 §7 열린 질문과 같은 문제).

안 먹는 설정 다이얼 388개(배선 319·**미배선 50**)와, 시드가 정책을 정해버린 사례
(`access.dept.원무과` 잔재가 운영 관리자를 잠갔다). 그래서 §6 에 **"기관 조정이 실제로 이긴다"**
가드를 넣었다 — 세팅 화면이 값을 받고도 아무것도 안 바꾸면 그게 가짜 다이얼이다.
