## 0. 왜 이 계획이 필요한가

급양 축 하나를 훑었더니 **한 도메인에서 실결함 11건**이 나왔다(v4.6.0 §13·§14·§15).
그중 어느 것도 "기능이 없어서"가 아니었다 — **있는데 이어지지 않았거나, 이어졌는데 거짓말을 했다.**

| 급양에서 나온 것 | 유형 |
|---|---|
| 8/21 등록이 8/20 에 저장 | `@db.Date` 로컬 자정 밀림 |
| 처방한 식이가 주방에 안 나감 | **오더가 실행에 반영되지 않음** |
| 퇴원해도 식이 처방이 활성 | **상위가 끝났는데 하위가 안 닫힘** |
| HACCP 이탈 시정조치가 항상 null | 서버는 받는데 **화면이 안 보냄** |
| HACCP 일지 조회 화면 부재 | 등록만 있고 **읽을 곳이 없음** |
| 배식·섭취율 실패를 삼킴 | `.catch` 로 실패가 성공으로 |
| 지원 직군 7종이 자기 알림 전원 403 | **전역 컴포넌트 × 최소 권한** |
| 급양사가 "할 일"을 알 수 없음 | **워크리스트 부재** |

🔴 **이 여덟 가지는 급양의 특성이 아니라 이 저장소의 관용구다.** 한 도메인에서 여덟 개가 나왔다면
다른 도메인에도 있다고 보는 것이 합리적이다. 그래서 **검사법을 고정하고 흐름마다 돌린다.**

## 1. 🔴 먼저 못박을 것 — "시드 ID로 만들어진 흐름"이란 무엇인가

운영 DB 는 가상 병원 시드다(CLAUDE.md 전제). 시드 비중 실측(2026-08-21):

| 테이블 | 전체 | 시드 UUID | 비중 |
|---|---:|---:|---:|
| diet_orders · safety_incidents | 3 · 75 | 3 · 75 | **100%** |
| dispensings · imaging_results | 330 · 209 | 327 · 206 | 99% · 98% |
| surgeries · orders · billings | 50 · 1,521 · 322 | 40 · 1,176 · 247 | 80% · 77% · 76% |
| nursing_notes · lab_results | 706 · 869 | 516 · 622 | 73% · 71% |
| prescriptions | 1,769 | 1,176 | 66% |
| admissions | 34 | 17 | 50% |
| meal_orders · encounters | 24 · 754 | 9 · 216 | 37% · 28% |
| emergency_visits · appointments | 186 · 577 | **186 · 548** | **100% · 95%** |
| checkup_visits | 105 | 0 | **0%** |

🔴 **2026-08-21 정정 — 이 표에 오답이 둘 있었다.** 시드 판별을 `00000000-0000-4000%` 하나로만
했는데 생성기가 접두를 **여러 개** 쓴다(`ee000000-0000-4000-…` 등). 정확한 판별은
`^[0-9a-f]{8}-0000-4000-`(결정적 UUID) 이다. 그래서 **응급 6%→100% · 예약 1%→95%** 로 뒤집혔다.
(다른 축의 오차는 1~4%p — prescriptions 66→67 · surgeries 80→84.)
**5단계 우선순위 근거였던 "응급은 실쓰기가 많다"는 틀린 전제였다.** 그래도 미루지 않고
계획대로 **눌러서 표본을 만들어** 진행했고, 그 표본이 실결함을 드러냈다(부록 E).
🔴 **내 도구가 먼저 거짓말한다 — 접두 하나로 집합을 정의하지 않는다.**

🔴 **비중이 높다 = 그 흐름은 "사람이 눌러서 생긴 것이 거의 없다"** 는 뜻이다.
시드가 만든 상태만 있고 **쓰기 경로가 한 번도 실행되지 않았을 수 있다** —
급양이 정확히 그랬다(`staff_meal_menus`·`staff_meal_requests` 0행이었는데 눌러보니 날짜가 밀렸다).

### 🔴 2차 정정 (2026-08-24) — 시드 표식은 하나가 아니다

위 정정은 "접두를 여러 개 쓴다"까지만 고쳤다. 그 뒤 두 축에서 **UUID 와 무관한 시드**가 또 나왔다.

| # | 표식 | 어디서 나왔나 |
|---|---|---|
| 1 | 결정적 UUID `^[0-9a-f]{8}-0000-4000-` | 전 축(위 1차 정정) |
| 2 | **컬럼 표식** — `billings.cashier_note = 'SEED-ERP-CALC'` | 7단계. UUID 는 평범한 랜덤이라 **17건을 "실쓰기"로 오판**했다 |
| 3 | **생성 시각 군집** — 하루에 대량 생성 | 8단계 사전조사. `checkup_visits` 105건 중 **98건이 2026-05-30 하루**. 사람이 하루에 98건을 넣지 않는다 |

🔴 **그래서 아래 문장은 틀렸다(취소선으로 남긴다 — 같은 오판을 반복하지 않기 위해):**
> ~~시드 0%인 흐름(checkup_visits)은 이 검사가 "표본 없음"으로 끝난다.~~

**"시드 UUID 0%" 는 "실쓰기 100%" 를 뜻하지 않는다. 그 축의 시드 표식을 아직 못 찾았다는 뜻일 수 있다.**

**흐름을 열 때의 표본 판정 절차(고정):**
1. UUID 접두로 1차 분류한다
2. **생성 시각 분포**를 본다 — `count(distinct created_at::date)` 와 일자별 top3.
   하루에 몰려 있으면 생성기다(사람의 쓰기는 흩어진다)
3. 그 축의 **컬럼 표식**을 찾는다(메모·비고·생성자 컬럼에 남는 경우가 있다)
4. 남은 것이 실쓰기다. 🔴 **그 수를 말하기 전에 표본 하나를 손으로 열어본다**

🔴 **표본이 전부 시드로 판정돼도 흐름을 미루지 않는다.** 그때는 코드를 읽고 **눌러서 표본을 만든다**
(5단계가 그랬다 — 우선순위 근거였던 전제가 틀렸는데도 눌러서 진행했고 실결함이 나왔다).

## 2. 검사법 — 흐름마다 이 9가지(A~I)를 돌린다

각 항목은 **기계 검사(자동)** 와 **사람 검사(눌러보기)** 로 나뉜다.
🔴 **기계 검사가 0을 내도 "결함 없음"이 아니다** — 표본이 없으면 판정 불가다. 그것을 그대로 적는다.

### A. 날짜 정합 `@db.Date` (기계)
`new Date('Y-M-D')` + `.setHours(0,0,0,0)` → KST 에서 **UTC 기준 전날**.
정본 `common/day-range.ts` 의 `dateOnlyValue`/`todayDateOnly`.
- 실측(2026-08-21): `@db.Date` 모델 **97개** · 해당 패턴을 쓰면서 그 모델을 건드리는 파일 **17개**
- 급양 2개는 해소. 🔴 **나머지 15개는 후보이지 확정 결함이 아니다**(timestamptz 구간용이면 정당)
- 판정: 파일별로 그 `setHours` 값이 **`@db.Date` 컬럼에 닿는지** 손으로 확인

### B. 오더 → 실행 반영 (사람 + 기계)
"처방/오더의 정본"과 "실행을 만드는 코드"가 **같은 것을 읽는가**.
- 급양: 화면은 활성 처방을 병합해 보여주는데 **식사 생성만 `admission.dietType`** 을 썼다
- 검사: 각 흐름의 실행 생성기(`generate*`·`create*`)가 읽는 필드 vs 화면이 정본이라 부르는 필드
- 🔴 **화면이 병합한 정본을 실행 경로도 쓰는지 확인한다**

### C. 상위 종료 시 하위 오더 종료 (기계)
입원/진료/방문이 끝나면 그 아래 오더도 끝나야 한다.
- 실측(2026-08-21): `admissionId` 를 가진 상태 테이블 11개 중
  · `diet_orders` 잔류 0(이번에 해소) · **`protocol_instances` 잔류 1건** 🔴
  · 나머지 8개는 **0행이라 판정 불가**(표본 없음)
- 판정: 표본이 있는 것만 결론 낸다. 0행은 **쓰기 경로를 눌러 표본을 만든 뒤** 다시 잰다

### D. 등록은 되는데 읽을 곳이 없는 기록 (기계 + 사람)
법정·필수 기록인데 **조회 화면 호출부 0**.
- 급양: `GET /nutrition/haccp` 호출부 0 — 급양과가 HACCP 일지를 볼 수 없었다
- 검사: 도메인별 GET EP 를 FE 전역 grep → 호출부 0 목록
- 🔴 **법정 기록은 등록 EP 만으로 부족하다**
- 🔴 **"있는 것"이 아니라 "없는 것"을 세는 지표가 있는가**(3단계 수술) — EP·화면이 다 있어도
  *누락을 세는 지표*가 없으면 드러나지 않는다. 관제가 있어도 **모집단 범위가 다르면**
  (30일 추세 vs 누적) 다른 질문에 답한다

### E. 화면이 서버가 받는 필드를 안 보내는가 (사람)
- 급양: 서버는 `correctiveAction` 을 받는데 화면이 안 보내 **이탈 시정조치가 개통 이래 항상 null**
- 검사: 쓰기 DTO 의 선택 필드 중 **운영 원장에서 전건 null 인 것** → 화면이 보내는지 확인
- 🔴 **전건 NULL 은 셋 중 하나다** — ①화면이 안 보냄 ②게이트가 꺼져 있음 ③**해당 사건이 없었음**.
  셋을 가르려면 **눌러봐야 한다**(1단계 투약에서 ②였고, 진짜 결함은 그 옆의 원장·관제에 있었다)

### F. 실패를 성공으로 접는 자리 (기계)
`.catch(() => 기본값)` — v4.6.0 §8 에서 `Promise.all` 24개소를 판정했으나 **그 밖은 안 봤다**.
- 검사: 흐름별 쓰기 경로의 `.catch` 전수 → 3상태로 말하거나 전파
- 🔴 **`.catch(()=>[])` 는 "실패"를 "없음"으로 번역하는 코드다**

### G. 상태 어휘 선언 (기계 — 저장값 전수 완료 · 코드 리터럴은 흐름별로)
🔴 **DB 값만 보면 부족하다** — 2단계에서 나온 flag 어휘 결함은 **아직 저장된 적 없는 값**이라
DB 스캔(130개 중 3건)에 걸리지 않았다. **코드가 쓰는 리터럴이 정본 목록에 있는지** 정적으로도 본다.

스키마 주석 vs 운영 원장 distinct 값 대조. **실측 결과 드리프트 3건뿐**:
| 테이블 | 원장에만 있는 값 |
|---|---|
| `meal_orders` | `UNDELIVERED` (이번에 정본화·해소) |
| `accreditation_items` | `PENDING` |
| `patient_communication_logs` | `SIMULATED` |
🔴 **이 축은 대체로 깨끗하다** — 남은 2건만 처리하면 된다. 없는 일을 만들지 않는다.

### H. 전역 컴포넌트 × 최소 권한 (사람 — 이번에 전수 완료)
`(main)` 레이아웃이 렌더하는 컴포넌트가 부르는 EP 를 **최소 권한 계정으로 실제 로그인해** 훑는다.
- 실측: 위급검사값 배너 **9역할 상시 403** · 자기 알림 **지원 직군 7종 전원 403** → 둘 다 해소
- 🔴 남은 전역 컴포넌트(AiChatBar·CertificationBadge·DailyPinPrompt·StepUpApprovalPrompt·SmartSearchBar·TopBar)는
  **아직 안 훑었다** — 계정 9종 × 전역 EP 프로브가 남아 있다

### I. 워크리스트 (사람)
입력 화면만 있고 **"누구를 처리해야 하는가"** 가 없으면 직원은 기억으로 일한다.
- 급양: 재원 5명 중 영양평가 **2명** · 상담 후속일 도래 **4건**이 어느 화면에도 없었다
- 검사: 직군별로 "오늘 할 일"이 한 화면에서 나오는가. 나온다면 **분모와 함께** 나오는가

## 4. 흐름 하나를 도는 절차 (급양에서 실제로 통한 순서)

1. **모델·EP·화면 지도** — 그 흐름의 테이블/EP/화면을 나열한다

3. **종단으로 눌러본다** — 생성 → 변경 → 종료까지. 응답만 보지 말고 **DB 원본을 확인**한다
4. A~I 검사 적용
5. **고칠 것과 정당한 것을 가른다** — 🔴 정당 판정에 억지 가드를 만들지 않는다
6. **재주입 역검증** — 고친 것을 되돌려 가드가 실패하는지 확인한다
7. **운영 재확인** — 배포 후 같은 종단을 다시 눌러본다. **검증 데이터는 지운다**

## 5. 🔴 이 계획이 스스로에게 거는 제약

- **후보와 확정을 구분해 말한다.** 스캔 수를 결함 수로 보고하지 않는다
  (급양 축에서 "17개 파일"은 후보였고 확정은 2개였다. 첫 스캔이 64건 오답을 낸 적도 있다)
- **0행은 결론이 아니다.** "표본 없음 · 판정 불가"라고 적고, 표본을 만들 방법을 함께 적는다
- **어휘를 지어내지 않는다.** 실제 저장값을 보고 정본을 만든다(급양에서 영문 enum 을 철회했다)
- **막지 않고 드러낸다.** 강제하면 거짓 데이터가 된다(v4.5.0). 기본값 폴백은 **분모와 함께** 표시
- **결함 0건도 유효한 결과다.** G축이 3건뿐이었던 것이 그 예다
- 🔴 **만들기 전에 이미 있는지 확인한다 — 키 이름 grep 으로만 하지 않는다.**
  같은 개념이 다른 이름으로 있을 수 있다(4단계에서 `summaryMissing` 을 못 찾고 중복을 만들 뻔했다).
  **도메인의 기존 지표 목록을 먼저 전부 읽고**, 나란히 놓았을 때 **왜 수가 다른지 라벨만으로 알 수 있게** 한다
- **내 도구가 먼저 거짓말한다.** 수치를 말하기 전에 표본 하나를 손으로 연다
- **운영 데이터를 만들었으면 지운다.** 검증 흔적을 원장에 남기지 않는다
- 🔴 **"SoT" 라고 주석에 적힌 것이 정본이라는 뜻은 아니다**(7단계). 읽는 코드가 0이면 그것은 정본이 아니라
  **아무도 안 보는 기록**이다. **주석이 아니라 소비처를 센다**
- 🔴 **요약 라벨로 집계하지 않는다**(7단계). `MIXED` 는 수단이 아니다 — 요약을 집계하면 그 뒤의 사실이 사라진다.
  같은 함정: 상태 문자열로 누적선량을 세다 조사분획을 놓친 것(v4.1.0)
- 🔴 **새 사건을 만들면 그것을 보는 화면까지가 한 벌**(7단계). 어휘만 만들고 큐·필터에 넣지 않으면
  기록만 쌓인다. 그 자리에서 **이진 삼항 라벨**(P10)도 함께 본다 — 종류가 셋이 되는 순간 거짓 라벨이 된다
- 🔴 **배포 후 눌러본 것까지가 한 단계다**(6·7단계 연속). 6단계는 배포 후에 4번째 결함이 나왔고,
  7단계는 배포 후에 **내 봉합이 만든 새 거짓말**(취소건이 수단별에만 잡혀 화면이 원인을 오설명)이 나왔다

봉합분을 배포한 뒤 절차 7번(*"배포 후 같은 종단을 다시 눌러본다"*)대로 운영에서

```

```

**저장된 촬영은 CT 인데 판정은 'OT'(미상)** 였다. `detectModality` 가 **시술코드 하나만** 보는데,
`procedureCodeId` 는 처방 DTO 전 경로에서 **선택**이다(`@IsOptional()`).

| 운영 실측 | 값 |
|---|---|
| 영상 결과 209건 중 시술코드가 달린 처방 | **46건(22%)** |
| CT 36 · MG 16 · MR 25 | **전건 0** |

그러면 조영·임신·누적선량이 **한 항목도 돌지 않고**, 화면은 그 빈 결과를 보고
"조영·방사선 검사 아님"이라 말한다. 🔴 **내가 방금 고친 화면이, 서버가 준 거짓 `ionizing:false`
때문에 여전히 같은 거짓말을 하고 있었다.**

🔴 **시드 산물이 아니라 코드 결함이다** — 시술코드 없는 영상 처방을 만드는 것이 실경로에서 가능하다.

지표도 하나 더 뒀다 — `imaging.procedureCodeMissing` **164 / 217**. 촬영 전에는 기록된 modality 조차
없으므로 시술코드가 없으면 사전 확인이 **구조적으로 판정 불가**다. 그 모집단의 크기를 화면이 말한다.

**고친 것** — 판정 정본 `resolveModality` 하나를 사전 확인과 시행 게이트가 **함께** 쓴다.
근거 우선순위 = 명시 입력 > 시술코드 > **이미 기록된 촬영의 modality**(추정이 아니라 그 오더에
실제로 적힌 사실) > `UNKNOWN`. 그래도 모르면 **지어내지 않고 밝힌다** — 응답에
`modalityKnown:false`·`modalitySource:'UNKNOWN'` 을 실어, 화면이
