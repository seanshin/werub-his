## 2. 공백 상세

### G1 🔴 QR 을 찍어도 대조할 곳이 없다

- **사실:** 해시는 인쇄하던 브라우저가 계산하고 어디에도 남지 않는다. QR 은 JSON 글자다.
- **결과:**
  - 위조 종이(내용을 고친 사본)를 가려낼 수 없다.
  - 원장이 바뀐 뒤에는 옛 판의 해시를 다시 만들 수도 없다(결정 하나가 바뀌면 대장 해시가 바뀐다).
- **판정:** 사용자 요청 "페이지마다 보안 인증"은 **표시만 있고 인증이 없는 상태**다(P17 — 근거 없이 안심시킴).

### G2 🔴 클라이언트 스냅샷 해시

- **사실:** `document.service.ts` `issue()` 가 요청 본문의 snapshot 을 그대로 동결·해시한다.
- **결과:**
  - 원장 파생 문서(결정 대장 등)를 이 경로로 발급하면, 발급 역할을 가진 누구든 도구로 임의 내용을 보내 진본 번호를 받는다.
  - `JSON.stringify` 는 키 순서에 의존하므로 같은 내용도 다른 해시가 날 수 있다.

### G13 🔴 문서 종류 허용 목록 없음

- **사실:** `IssueDocumentDto.documentType` 은 `@IsString()` 하나다.
- **결과:** G2 를 막으려고 새 서버 발급 EP 를 만들어도, **기존 범용 EP 로 같은 종류를 보내면** 우회된다.
  - 예: 의사 역할로 `{ documentType: 'DECISION_REGISTER', snapshot: {...} }`
- 서버 생성 종류는 범용 EP 가 거부해야 한다.

### G12 발급번호 UTC 날짜

- **사실:** `dateKey` 가 UTC 다. 한국 시간 10-12 08:30 발급은 `…-20261011-…` 로 찍힌다(판정 규칙 §7 날짜 밀림).
- **처리:**
  - 새 발급부터 한국 날짜로 매긴다.
  - 🔴 **이미 발급된 번호는 바꾸지 않는다**(일어난 사실은 소급하지 않는다 — 종이에 이미 찍혔다).
  - 바뀌는 날을 릴리즈 문서에 적는다.

### G14 순번 열거

- **사실:** 공개 진위확인은 번호만 있으면 답한다. 번호가 순번이라 날짜·종류를 알면 그날 발급 수와 시각이 드러난다.
- **처리:** 내부 문서(서버 생성 종류)는 QR URL 에 **확인 코드**(`v=` HMAC 앞 10자)를 붙인다. 코드가 맞을 때만 답한다.
  - 저장 컬럼 없이 서버 비밀로 다시 만든다 → 스키마 변경 없음.
  - 기존 종류는 종이에 찍힌 QR 이 이미 있으므로 **바꾸지 않는다**(호환).

### G15 진위확인 종류 라벨

- **사실:** 화면 라벨 표가 6종이라 사망진단서 등은 `DEATH_CERT` 가 그대로 보인다.
- **처리:** 라벨 정본을 shared 로 옮긴다. 렌더러 종류 ⊆ 라벨 키를 가드로 강제한다.

### G3 인쇄 감사

- **사실:** `PrintAttempt` 감사는 차단·허용과 경로만 남긴다.
- **처리:** 발급번호·종류·해시 앞 16자를 `detail` 에 싣는다(200자 안 · DTO 변경 없음).

### G4 QR 체계 둘

- **처리:** 진위확인 URL 하나로 수렴한다. 발급 원장에 올리지 않는 인쇄본(단축키 등)은 QR 을 싣지 않는다 — JSON QR 은 없앤다.

### G6·G16 🔴 개발 반영 추적 + 시드가 정한 정책

- **G6 사실:**
  - 개발 반영 결정 108건은 의사결정 뒤 개발이 그 선택대로 반영했는지 기록하지 않는다.
  - 이행 5상태(판정 규칙 §6) 밖에 있다 — "기록됨"에서 멈춘다.
- **G16 사실:**
  - 시드가 동작 변경 선택지를 고른 개발 반영 결정이 **47건**이다.
  - 그중 일부는 시드 시점이나 그 전에 **이미 그대로 구현됐다** — 예: `journey.outpatientEnd` = 수납 완료, `emergency.departureTimeSource` = 퇴실 시각 칸, `surgery.durationDefinition` = 수술실 체류.
  - 시드는 실결정이 아닌데 **시스템 동작은 시드의 선택을 따른다**.
- **위험:**
  1. 실결정이 시드와 다르게 나오면 이미 구현된 동작을 **되돌려야** 한다. 지금은 그 사실을 아무도 모른다.
  2. 실결정이 시드와 같으면 "이미 반영됨"인데 "반영 대기"로 보인다.
  3. CLAUDE.md 함정 #4 "시드가 정책을 정해버린다"가 결정 축에서 47건 규모로 재현된다.
- **판정 불가:** 키를 읽는 코드가 5/108 뿐이라 **기계로 판정할 수 없다**. 사람(개발)이 키마다 판정해야 한다 → P2-0.

## 3. 설계

### P0 — 결정 인쇄본 발급 원장 + 발급 원장 기존 결함

#### P0-1 정본 줄(v1) — 서버·화면 공용

```
줄    = 결정키 "|" 상태 "|" 선택값 "|" 결정시각
상태  = REAL | SEED | OPEN        (decided → REAL · seeded → SEED · 그 밖 OPEN)
선택값 = 기록의 choice 코드(없으면 빈 문자열)
결정시각 = 기록의 decidedAt ISO 문자열 그대로(없으면 빈 문자열)
정렬  = 세부 분류 정본 순서(DECISION_SUBDOMAINS) → 결정 키 사전순   (대장)
본문  = 줄들을 "\n" 으로 이음(UTF-8) · 해시 = sha256 hex
```

- 화면 `printCanonLine`(v4.67.0)과 **같은 함수**를 shared 로 옮겨 서버·화면이 하나를 쓴다(정본 하나).
- 키·코드에 `|`·줄바꿈이 없다는 것을 가드로 강제한다(등록부 전 키·전 선택값).

#### P0-2 서버 발급 EP

```
POST /api/v1/admin/decisions/print-issue        @Roles(ADMIN)  (D3 확정 전 기본값)
본문 { kind: 'REGISTER' | 'RECORD', key?: string }      // RECORD 면 key 필수
응답 { issueNo, documentType, issuedAt, hash, verifyUrl, lines: number }
오류 400 PRINT_ISSUE_KEY_REQUIRED · 404 DECISION_NOT_FOUND · 500 ISSUE_FAILED(원인)
```

- 서버가 결정 목록(서비스 `list()` 와 같은 파생)을 읽어 정본 줄을 만든다. 🔴 본문에 snapshot 이 와도 무시한다.
- 스냅샷:
  - 형태: `{ v: 1, kind, key?, measuredAt, counts: { REAL, SEED, OPEN }, lines: string[] }`
  - 해시는 `lines.join('\n')` 의 sha256 — `JSON.stringify` 순서 의존을 피한다.
- 발급은 `DocumentService` 에 서버 전용 메서드 `issueBuilt(type, sourceId, snapshot, hash)` 를 두고 채번·동결을 재사용한다.
- documentType: `DECISION_REGISTER`(sourceId `register`) · `DECISION_RECORD`(sourceId = 결정 키).
- 감사: 기존 발급 감사와 같은 형태(`IssuedDocument:<type>`).

#### P0-3 범용 발급 EP 잠금(G2·G13)

- 정본 `SERVER_BUILT_DOCUMENT_TYPES`(shared): `DECISION_REGISTER` · `DECISION_RECORD` + P1 종류.
- `POST documents/issue` 가 이 종류를 받으면 `400 DOCUMENT_TYPE_SERVER_BUILT`.
- `reissue` 는 원본 스냅샷을 복사하므로 허용한다(서버가 만든 스냅샷).
- 범용 EP 의 허용 목록(기존 14종 + 운영에 있는 종류)은 **운영 실측 종류를 먼저 센 뒤** 정한다. 지금 운영에 `CHECKUP_RESULT`·`CONTRACT`·`CONSENT` 가 있다 → 렌더러가 없는 종류가 있는지 함께 본다.

#### P0-4 확인 코드(G14)

- `v = base32(HMAC_SHA256(DOC_VERIFY_SECRET, issueNo))` 앞 10자.
- 비밀은 `release-security.ts` 정본에 등재한다 — REAL 빌드는 폴백이면 부팅 거부(기존 비밀들과 같은 규약).
- 서버 생성 종류의 `GET documents/verify/:issueNo?v=` 응답:
  - `v` 가 없거나 틀리면 `{ valid: false, reason: 'CHECK_CODE' }`
  - 🔴 "발급 기록 없음"과 다른 사유로 답한다 — 위조와 오타를 구분해 말한다
- 기존 종류는 `v` 없이 종전대로(호환).

#### P0-5 진위확인 화면

| 보는 사람 | 보이는 것 |
|---|---|
| 공개(로그인 없음) | 유효/무효/조회 실패 3상태 · 문서 종류(한국어 라벨) · 발급 시각 · 상태 · 기관명 — 🔴 결정 내용 없음 |

- "지금 원장과의 차이":
  - 서버가 지금 정본 줄을 다시 만들어 발급 스냅샷의 줄과 키 단위로 대조한다.

| `DEV_REVERT_NEEDED` | 실결정 ≠ 이미 구현된 시드 동작 | 되돌릴 범위 |

- `DEV_REVERT_NEEDED` 는 실결정 기록 순간 **서버가 자동으로** 남긴다(P2-0 이 `시드대로 구현됨` 이고 실결정 선택 ≠ 시드 선택일 때).
- 나머지 둘은 관리자가 근거와 함께 남긴다(D5).

**P2-2 이행 상태**(개발 반영 결정에만):

| 상태 | 조건 |
|---|---|
| 미결 | 실결정 없음(시드 포함 — 🔴 시드는 이행 상태를 만들지 않는다) |
| 반영 대기(개발) | 실결정 있음 · DEV_ENACTED/NOT_REQUIRED 없음 |
| 되돌림 필요 | DEV_REVERT_NEEDED 이후 DEV_ENACTED 없음 |
| 반영됨(vX) | DEV_ENACTED |
| 반영 불필요(현행) | DEV_NOT_REQUIRED |

- 🔴 "반영 대기"를 "반영됨"과 같은 색으로 그리지 않는다.
- 체류일(실결정 후 경과일)은 사실로만 보이고, 지연 판정은 하지 않는다.

## 6. 하지 않는 것·한계

- **쪽마다 다른 QR:** CSS 여백 상자는 쪽마다 다른 이미지를 못 그린다. 쪽 수는 인쇄 때 브라우저가 정한다. 쪽 바꿔치기는 "발급번호 · 쪽 n/N" 글자로 사람이 대조한다. 쪽 단위 진위는 서버 PDF(browserless)로 쪽을 서버가 정해야 하며 범위 밖이다.
- **스크린샷·OS 캡처**는 막지 못한다(PrintGuard 한계).
- 실결정을 시스템이 대신하지 않는다. 시드는 실결정이 아니다.
- 기존 발급번호(UTC 날짜)는 고치지 않는다.
