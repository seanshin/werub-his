# 전체 흐름(환자 여정 종단) 검토 계획 — 2026-07

> 대상: 운영(`his.example.org`) · 작성 2026-07-28 · 기준 버전 v3.74.0
> 성격: **개별 기능 감사가 아니라 흐름이 끝까지 이어지는지**를 보는 종단 검토

## 1. 왜 지금 이 검토인가

최근 8개 트랙(무가드·크론·화면 도달성·여정 이벤트·감사 커버리지·입력 검증·파일 접근)은 모두
**단일 축을 전수로 훑는** 방식이었다. 축별로는 촘촘하지만, 축을 가로지르는 질문에는 답하지 못한다.

> 환자 한 명이 접수부터 수납까지 지나갈 때, **모든 축이 동시에 정상 동작하는가?**

특히 여정 이벤트 트랙에서 드러난 실패 유형이 이 검토의 근거다 —
개별 기능은 다 있는데 **연결이 없어서** 실 환자 여정이 비어 있었다.
같은 형태의 단절이 다른 흐름에도 남아 있는지 본다.

## 3. 검증 방식

각 단계마다 **세 층**을 함께 본다. 한 층만 보면 v3.71 여정 갭처럼 "화면은 되는데 기록은 없는" 상태를 놓친다.

| 층 | 확인 대상 | 증거 |
|---|---|---|
| **API** | 엔드포인트가 살아 있고 계약대로 응답하는가 | HTTP 상태 · 응답 필드 |
| **데이터** | 그 행위가 DB 에 남았는가 | 운영 DB 직접 조회(행 수·상태값) |
| **횡단** | 감사·여정·알림이 함께 발생했는가 | `audit_logs` · `journey_events` · `notifications` 증분 |

**판정 등급**

- **PASS** — 세 층 모두 기대대로
- **GAP** — API 는 정상인데 데이터·횡단이 비어 있음(여정 갭 유형)
- **FAIL** — API 자체가 실패(404/500) 또는 계약 불일치
- **N/A** — 운영 데이터 부재로 확인 불가(사유 기록)

## 4. 운영 안전 규약

운영 시스템에서 수행하므로 다음을 강제한다.

1. **읽기 우선.** 각 흐름은 먼저 조회로 현재 상태를 확인하고, 쓰기는 필요한 최소 지점에만 한다.
2. **쓰기는 데모/검증 데이터에 한정.** 실 환자 기록은 생성·수정하지 않는다.
3. **금전·법정 기록 전이 금지.** 실 수납 처리, 실 처방 발행, 실 퇴원 정산 확정, 동의서 서명 확정은 수행하지 않는다 — 조회·시뮬레이션 EP 로 대체한다.
4. **파괴적 프로브 금지.** 삭제·대량 갱신·마스터 덮어쓰기는 시도하지 않는다(입력 검증 트랙에서 확인된 주입 벡터도 **비파괴 판별**만 사용).
5. **생성분은 즉시 정리.** 생성한 검증 리소스는 같은 세션에서 취소·삭제하고 정리 사실을 기록한다.
6. **증거 보존.** 각 판정은 HTTP 상태·DB 수치를 함께 남긴다. "동작했다"는 서술만으로는 근거가 되지 않는다.

파일 접근은 서명 URL 발급·게이트 동작을 확인한다(v3.74 봉합분 회귀).

### 7.2 세 층 동시 검증 — 가역 쓰기 프로브 1건

운영 안전 규약(§4)에 따라 **비임상·가역** 지점 한 곳에서만 쓰기를 수행했다.

| 시점 | 여정 이벤트 | 감사 로그 |
|---|---:|---:|
| 생성 전 | 371 | 4,354 |
| 예약 1건 생성 후 | **372** | **4,355** |

- 여정 증분 = `APPOINTMENT_BOOKED`(v3.71 배선분)
- 감사 증분 = `CREATE | Appointment | <id>` · `changes={"fields":{"new":"patientId,doctorId,scheduledAt,type,reason"}}` (v3.72 봉합분 — **PHI 값이 아니라 필드 키만** 기록되는 것까지 확인)
- **정리 완료**: 해당 예약 `CANCELLED` 전이(운영 잔여물 없음)

즉 **API → 데이터 → 횡단(여정·감사)** 이 한 행위에서 동시에 성립함을 실증했다.

### 7.3 결함이 아니었던 것 — 프로브 오류 3건

종단 검토에서 404/400 이 나오면 **먼저 프로브를 의심해야 한다.** 실제로 초회 실행의 실패 대부분이 내 프로브 오류였다.

| 초회 관측 | 원인 | 정본 계약 |
|---|---|---|
| `/lab/results`·`/imaging/results`·`/lab/orders` 404 | 경로 추정 오류 | `/lab/patients/:id/results` · `/imaging/patients/:id/results` · `/lab/queue` |
| `availability?departmentName=내과` 400 | **한글 쿼리 URL 미인코딩**(nginx 400) | 인코딩 시 200 |
| 예약 취소 사유 미저장 | 필드명 오기(`reason`) → `whitelist:true` 가 제거 | 정본은 `cancelReason` |

세 번째 건은 v3.73 에서 확인한 `whitelist: true` 의 동작(선언되지 않은 필드는 조용히 잘림)이
**설계대로 작동한 사례**다. 동시에 "일괄 DTO 도입이 위험한 이유"의 실물 예이기도 하다.

### 7.4 관측 (결함 아님 · 후속 판단 대상)

1. **단건 조회 EP 부재** — `GET /api/v1/orders/:id`·`/prescriptions/:id` 는 없고 환자/진료 스코프 목록만 존재한다.
   FE 가 목록 기반이라 현재 문제는 없으나, 외부 연동이 단건 조회를 요구하면 계약 추가가 필요하다.
2. **여정 이벤트 최신값 편차** — `PRESCRIPTION_ADDED`·`IMAGING_RESULT` 의 최신 이벤트가 5월이다.
   v3.71 배선(7/28) **이후 해당 행위 자체가 발생하지 않았기 때문**이며, 배선 이후 발생한
   `ORDER_CREATED`·`LAB_RESULT` 는 당일자로 정상 발행됐다(§7.1) — 배선 결함이 아니다.
3. **데이터 품질 지표가 높다** — 전화 미등록 825/873 · 보험 미확인 873 · 주소 미등록 865.
   기존 백로그의 **마스터 큐레이션(사람 몫)** 항목과 일치한다.
4. **운영 트래픽이 낮다** — 최근 7일 진료 1건·청구 2건. 종단 검증을 신규 생성이 아니라
   **기존 데이터 조회 + 가역 쓰기 1건**으로 설계한 이유이며, 향후 실사용 증가 시 재실행이 필요하다.

### 7.5 결론

- 8개 흐름 전부에서 **끊긴 구간(FAIL/GAP)이 발견되지 않았다.**
- 최근 8개 트랙의 봉합분(여정 배선 v3.71 · 감사 커버리지 v3.72 · 입력 검증 v3.73 · 파일 접근 v3.74)이
  **운영에서 실제로 동작함**을 종단 관점에서 재확인했다.
- 남은 개선은 결함이 아니라 **데이터 큐레이션(사람)** 과 **트래픽 축적 후 재검증**이다.

### 7.6 재사용 — 회귀 프로브 스크립트

§7.3 의 정본 경로를 반영한 **읽기 전용** 프로브를 스크립트로 남겼다.

```bash
HIS_TOKEN=<직원 JWT> ./infra/scripts/e2e-flow-probe.sh
```

교정본 재실행 결과 **40개 프로브 전부 200**. 릴리즈 직후 이 스크립트를 돌려
흐름이 끊기지 않았는지 한 번에 확인한다(비200 이 나오면 계획서 §7.3 을 먼저 확인 — 앵커 ID·경로 오류일 수 있다).

**후속 권고**: 실사용 트래픽이 축적된 뒤 §7.2 형태의 세 층 동시 검증을 F1(외래 처방)·F4(퇴원 정산) 지점에서 재실행한다.
