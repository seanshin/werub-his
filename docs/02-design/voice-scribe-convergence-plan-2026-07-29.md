# 스크라이브 × VoiceEMR — 기반 공유·각자 발전 전략 계획서 (2026-07-29)

**결정**: 두 음성 기능을 하나로 합치지 않는다. **코어는 각자 발전**, **기반(substrate)은 공유**한다.
수렴은 "하나의 기능"이 아니라 **하나의 세션·두 소비자**(성문이 문서화/명령을 라우팅)로 달성한다.

관련: [[ambient_clinical_scribe]] [[voice_emr_speaker_enroll]] [[triage_ai_api]]

---

## 1. 왜 합치지 않는가 (본질 분석)

두 기능은 "입력이 음성"일 뿐, 요구사항이 정반대 축에 있다.

| 축 | 📝 스크라이브(문서화) | ⌨️ VoiceEMR(명령) |
|---|---|---|
| 사용자 자세 | 수동·핸즈오프(대화를 듣기만) | 능동·지시(PTT로 시스템에 명령) |
| 성격 | 서사·비정형 | 구조화·정형 |
| 지연 예산 | 배치(사후·수십 초 허용) | 실시간(저지연 필수·응답성) |
| AI 경로 | `/api/meeting/analyze`(화자분리 배치) | `/api/stt/chunk`(스트리밍) |
| 오류 내성 | **높음**(초안·의사 수정·서명) | **낮음**(오인식=안전사고→확인게이트) |
| 출력 | SOAP 초안(prose) | 게이트된 구조화 액션(오더·활력·필드) |
| 안전 모델 | 녹음 동의·문서 정확도 | 명령 확인·환자 신원·DUR·고위험 2단계 |
| 성공 지표 | 차팅 시간↓·요약 품질 | 명령 정확도·응답성·오더 안전 |

**핵심 리스크**: 한 코드경로로 묶으면 서로의 품질기준이 상대를 잡아당긴다.
- 명령 경로가 배치 지연을 물려받음 → 실시간성 상실(사용 불가)
- 문서화 경로가 엄격한 확인게이트를 물려받음 → prose 흐름 저해(거슬림)
- 롤아웃 결합: 스크라이브=⏸BACKLOG(GPU/large-v3 OOM), VoiceEMR=write/order 게이트 OFF·READ만 개방 → 성숙도·게이트 상태가 달라 코어 결합 시 배포가 엉킴.

→ **각자 발전이 옳다.**

## 2. 각 기능의 독립 방향성(로드맵)

### 2-A. 스크라이브 (문서화 코어)
목표: 진료 대화 → 신뢰할 수 있는 SOAP 초안. **차팅 부담 절감**이 KPI.

| 단계 | 항목 | 상태/게이트 |
|---|---|---|
| S1 | 녹음→업로드→화자분리→전사 뷰어→SOAP 초안→적용 | 배포·⏸BACKLOG(STT GPU) |
| S2 | 화자 귀속(의사 vs 환자) — 성문 연동 | 기반 공유 대기(§3) |
| S3 | 의료 NER·구조화 추출(문제·약물·계획 언급) | 기획 |
| S4 | 다자간(회진·다직역 협진) 화자분리 | 테스트 배선(/settings/voice) |
| S5 | 요약 품질·템플릿별 SOAP·인용(근거 세그먼트) | 기획 |

독립 축: **배치 STT 품질**, **요약/추출 정확도**, **문서 신뢰성**. 실시간성 불필요.

### 2-B. VoiceEMR (명령 코어)
목표: 핸즈프리 EMR 조작. **명령 정확도·안전**이 KPI.

| 단계 | 항목 | 상태/게이트 |
|---|---|---|
| V1 | READ(조회)·구술 필드·확인 카드·감사 | 배포·READ 개방 |
| V2 | 활력·오더 명령 + 확인게이트(환자신원·DUR·고위험 2단계) | write/order OFF |
| V3 | 개인화(별칭·습관·어휘·매크로)·코드매칭(퍼지·초성) | 배포(개인화)·확장 |
| V4 | 화자 게이트(내 음성만 명령) — 성문 연동 | 기반 공유 대기(§3) |
| V5 | 실 EMR 쓰기 배선(기존 오더/활력 EP 재사용·중복방지) | 승인 대기 |

독립 축: **실시간 STT 저지연**, **intent 파싱**, **오더 안전게이트**. 배치 불가.

## 3. 공유 기반 (substrate) — 정본

두 코어가 공유하는 하부 구조. **한 곳에서 관리하고 양쪽이 소비**한다.

| # | 공유 자산 | 정본 위치 | 현황 |
|---|---|---|---|
| B1 | 🎙️ 마이크(장치·감도) | `MicSettings`·localStorage `voice.micDeviceId/micGain` | ✅ 통합 |
| B2 | 🗣️ **화자 성문(speaker ID)** | `VoiceUserProfile.voiceprint*`·WeRU.B `/api/speaker/*` | 배선·계약 대기(fail-open) |
| B3 | STT/AI 서버 연결 | config `ai.server.*`(url·gpuKey·enabled) | ✅ 공유(prod SET) |
| B4 | 임상 어휘 바이어싱 | `@hospital-run/shared` fuzzyCodeSearch·개인 VOCAB | ✅ 공유 |
| B5 | UI 단일 진입점 | `VoiceHub`(진료 헤더)·`/settings/voice` | ✅ 통합 |
| B6 | 녹음 동의/생체 동의 | 스크라이브=녹음동의·VoiceEMR=성문 §23 동의 | 각자·패턴 공유 |
| B7 | config 네임스페이스 | `voiceEmr.*`·`scribe.*` | 분리 유지(게이트 독립) |

**B2가 두 기능을 잇는 접착제다.** 성문 하나로:
- 스크라이브 → 세그먼트를 "의사"로 귀속(S2)
- VoiceEMR → 명령을 의사 음성으로 게이팅(V4)

→ 성문은 **공유 자산**이지, 코어를 녹이는 지점이 아니다.

### 3-1. B2 성문 공유 인터페이스 계약 (linchpin 명세)

성문이 유일한 코어 접점이므로, 두 코어가 **같은 함수 시그니처**로 소비해 결합도를 성문 1점에 가둔다.

```
// 공용 판정 함수(양 코어가 동일 인터페이스로 호출)
matchSpeaker(userId, audioOrEmbedding) → { isEnrolled, score: 0~1, isOwner: score≥τ }
```

| 항목 | 규격 |
|---|---|
| 입력 | 발화 임베딩(ECAPA 192-dim) 또는 raw PCM 16k(서버가 임베딩화) |
| 등록 정본 | `VoiceUserProfile.voiceprintRef`·WeRU.B speaker id=HIS userId |
| 임계값 τ | config `voiceEmr.speaker.threshold`(기본 0.7·튜닝) |
| 스크라이브 소비 | 세그먼트별 score → `isOwner`면 "의사", 아니면 "환자/기타" 라벨 |
| VoiceEMR 소비 | PTT 구간 score → `isOwner` 아니면 **명령 무시**(fail-closed 옵션) |
| 미가용(계약 前) | `isEnrolled=false` 반환 → **fail-open**: 스크라이브=화자번호만, VoiceEMR=마이크 분리 신뢰 |
| 오분류 안전 | VoiceEMR은 성문 통과해도 **확인게이트 유지**(성문은 1차 필터, 최종 안전 아님) |

**핵심 안전 원칙**: 성문은 편의(내 음성 선별)이지 **인증이 아니다**. 오더·활력 명령은 성문 통과 여부와 무관하게 환자신원·확인카드·DUR 게이트를 항상 거친다.

## 4. 수렴점 — "하나의 세션·두 소비자" (최종 형태)

기능 통합이 아니라 **동시 운용**이 목표.

```
        ┌─────────────── 하나의 마이크 세션 ───────────────┐
        │                                                  │
   [앰비언트 스트림]                              [PTT 구간]
        │                                                  │
   화자분리(배치)                                  스트리밍 STT
        │                                                  │
   성문: "의사/환자" 귀속                    성문: "의사?"→명령 인정
        │                                                  │
   📝 스크라이브(SOAP 초안)                  ⌨️ VoiceEMR(오더·활력·필드)
```

- 진료 내내 앰비언트가 배경에서 돌며 SOAP를 만든다.
- 의사가 "오더: 흉부 X-ray"처럼 PTT(또는 트리거어)로 말한 구간만 명령으로 분기.
- 성문이 "지금 말한 사람이 의사"를 판정해 문서/명령을 라우팅.
- **전제**: WeRU.B 성문 계약(`/api/speaker/*`) 확정 + 스트리밍/배치 동시 세션 운용.

## 5. 단계별 실행 계획

### Phase 0 — 기반 정리 (진행 중·대부분 완료)
- [x] 마이크 설정 통합(MicSettings)
- [x] UI 단일 진입점(VoiceHub)·디자인 통일
- [x] 성문 등록 UI·BE·동의(§23)·철회 파기 — fail-open 배선
- [x] STT/어휘 공유
- [ ] WeRU.B 성문 계약(`/api/speaker/enroll·delete`) 확정 — **외부 대기**(요청서 발송됨)

### Phase 1 — 성문 연동 활성 (계약 확정 후)
- [x] **선배선(2026-07-29)**: §3-1 공용 인터페이스 `SttChunkClient.matchSpeaker`(fail-open) + 게이트 플래그 `voiceEmr.speaker.enabled`/`.threshold`(0.7)·`scribe.speaker.enabled`(전부 OFF). 계약 확정 시 즉시 활성.
- [ ] 스크라이브 S2: 화자분리 세그먼트에 `matchSpeaker` 대조 → "의사/환자" 라벨 확정
- [ ] VoiceEMR V4: `speakerGateEnabled` + `matchSpeaker` 실동작(내 음성만 명령·타인 발화 무시)
- [ ] **대기**: WeRU.B `/api/speaker/enroll·match·delete` 계약 확정(현재 405·요청서 발송됨)

### Phase 2 — 동시 세션 프로토타입 (⚠ go/no-go 게이트)
**착수 전제(모두 충족 시에만 시작)**:
1. Phase 1 완료 — 성문 계약 활성 + 화자 게이트/귀속 실동작
2. 성문 라우팅 정확도 ≥ 목표(§KPI: 의사/환자 오분류 ≤ 3%)
3. WeRU.B가 **배치+스트리밍 동시 세션** 수용 확인(용량 협의) — 미확인 시 **착수 금지**(순차 유지)
4. 실측 수요 — 의사가 "기록 중 명령"을 실제로 요구하는지(파일럿 피드백). 수요 없으면 Phase 2 보류하고 각자 심화에 집중.

- [ ] 한 getUserMedia 스트림을 배치(스크라이브)·스트리밍(명령) 두 소비자에 분기
- [ ] PTT/트리거어로 명령 구간 마킹 → 그 구간만 스트리밍 STT
- [ ] 성문 라우팅 검증(의사 명령 vs 환자 발화 오분기 목표치 이하)

> **주의**: Phase 2는 "있으면 좋은" 수렴이지 필수가 아니다. 각자 발전(S/V 로드맵)이 항상 우선이며, Phase 2는 수요·용량·정확도가 모두 확인될 때만 진행한다.

### Phase 3 — 실 EMR 쓰기·확대
- [ ] VoiceEMR V5: 확인 후 기존 오더/활력 EP 배선(중복방지·감사)
- [ ] 스크라이브 S3~S5: NER·구조화 추출·요약 품질
- [ ] 회진·다직역 다자간 기록(다자간 화자분리 → 발화자별 기여)

## 6. 경계 원칙 (혼선 방지)

1. **코어 코드는 분리**한다. 공유는 §3의 B1~B7 자산에 한한다.
2. **config 게이트는 독립**(`voiceEmr.*` ≠ `scribe.*`). 한쪽 롤아웃이 다른쪽을 막지 않는다.
3. **안전 모델은 각자**: 스크라이브=녹음동의·초안, VoiceEMR=명령확인·오더안전. 서로의 게이트를 강요하지 않는다.
4. **성문(B2)만이 유일한 코어 접점**. 그 외 코어 결합은 금지(품질기준 상호 오염 방지).
5. 신규 공유 자산이 생기면 이 문서 §3에 등재 후 양쪽이 소비.

## 8. 성공지표(KPI) — 각자·수렴

| 대상 | 지표 | 목표 | 측정 |
|---|---|---|---|
| 스크라이브 | SOAP 초안 채택률(편집 후 서명) | ≥ 60% | 초안→서명 diff |
| 스크라이브 | 전사 WER(임상 어휘 가중) | ≤ 15% | 골든셋 대조 |
| 스크라이브 | 차팅 시간 절감 | ≥ 30% | 파일럿 전후 |
| VoiceEMR | 명령 인식 정확도(intent+슬롯) | ≥ 90% | 확인 카드 수락률 |
| VoiceEMR | 오더 오확정(틀린 약/용량 확정) | **0건** | 감사·역추적 |
| VoiceEMR | 명령 응답 지연(발화 종료→카드) | ≤ 2s | 클라 계측 |
| 공유(성문) | 화자 오분류(의사↔환자) | ≤ 3% | 라우팅 검증셋 |

> 오더 오확정 0건은 타협 불가(안전 임계). 나머지는 파일럿 기준선으로 조정.

## 10. 저하(degradation) 매트릭스 — 무엇이 죽으면 무엇이 남나

| 장애 | 스크라이브 | VoiceEMR | 원칙 |
|---|---|---|---|
| AI 서버 down(`ai.server.enabled=false`) | 녹음만·전사 보류(수동 작성) | 세션 시작 실패·키보드 입력 | fail-open·진료 무중단 |
| 성문 EP 미가용(현재) | 화자 번호만(귀속 없음) | 마이크 분리 신뢰·게이트 OFF | fail-open |
| 마이크 권한 거부 | 수동 작성 | 키보드 입력 | 논블로킹 |
| config OFF(각 게이트) | 미노출 | 미노출 | 독립 게이트 |
| 화자분리 스키마 불일치(D-2) | 단일 화자/평문 폴백 | 무관 | 방어적 파싱 |

**불변식**: 어떤 음성 장애도 **진료·서명 흐름을 막지 않는다**(항상 수동 폴백).

## 12. 검증 전략

- **성문 라우팅 검증셋**: 의사/환자 발화 라벨링된 다자간 클립 → 오분류율 측정(R1·KPI). 회귀 고정.
- **명령 안전 계약 테스트**: order.enabled OFF에서 오더 명령 403·확인 없는 확정 거부·고위험 2단계 강제.
- **저하 계약 테스트**: AI OFF·성문 미가용·권한 거부 각각에서 진료 흐름 무중단 확인(§10).
- **substrate 회귀**: B1~B7 변경 시 양 코어 스모크(마이크 캡처·성문 시그니처·STT 연결).
- **골든셋**: 임상 어휘 전사 WER·intent 파싱 정확도 골든 유지(이미 golden 12/70 존재).

## 13. 요약

- **각자 발전**: 스크라이브(문서화·배치·관용)와 VoiceEMR(명령·실시간·안전임계)는 요구사항이 반대라 코어를 분리 유지.
- **기반 공유**: 마이크·성문·STT·어휘·UI 진입점·동의패턴(B1~B7). 성문(B2)이 두 기능을 잇는 유일한 접점.
- **수렴은 동시 운용**: "하나의 세션·두 소비자"로, 성문이 문서화/명령을 라우팅. 성문 계약 확정이 선결.
